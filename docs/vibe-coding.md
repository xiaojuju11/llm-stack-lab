# vibe coding 规约

用 AI 写代码不是问题，**用 AI 写完还骗自己「我学会了」才是问题**。这份规约是为了让 AI 成为杠杆而不是拐杖。

## 五条硬规则

**1. 接口我先定，实现交给 AI。**
每个模块动手前，我先写下：输入是什么、输出是什么、失败时返回什么、有哪些边界情况。这份「契约」写不出来，说明我还没想清楚，此时让 AI 写只会得到一堆看起来能跑的垃圾。

**2. 每一行代码我都要能解释。**
提交前随机挑 5 行问自己「这行为什么这么写，换成别的写法会怎样」。答不上来的，删掉重写，或者去查文档——不许留着。

**3. 报错必须我亲自读。**
AI 给的「修复方案」直接粘贴会让报错消失，但根因没进我脑子。规矩是：先读完整报错、自己定位到文件和行、猜出原因，再去问 AI 对不对。猜错也比赛过更有价值。

**4. 不许一次生成超过 60 行。**
超过 60 行，我读的速度跟不上生成的速度，等于没读。宁可拆成三次。

**5. 每个专题至少有一块「裸写」。**
选该专题最核心的一处（比如 Agent 循环、检索链路），关掉 AI 手写一遍。写不出来说明这个专题没学完。

## 每次提交前的检查表

```
[ ] 代码我自己跑通了（不是"AI 说能跑"）
[ ] 我知道每一行为什么存在
[ ] 密钥没有硬编码，走的是 .env
[ ] 报错信息我读过原文
[ ] 复盘区填了当天的坑
```

## Prompt 记录模板

值得留的 prompt 记在对应专题 README 的「AI 协作记录」里，格式：

```markdown
### 场景：给工具调用加最大轮次保护
我问：<一句话概括需求 + 我定的接口契约>
AI 给：<一句话概括它做了什么>
我改了：<哪一处不认同，为什么>
结论：<这次 AI 帮到了什么，哪里差点带偏我>
```

记录 20 条之后，你会发现自己真正缺的不是「prompt 技巧」，而是**把需求描述清楚的能力**——那才是工程能力的核心。

## 什么时候不该用 AI

- 学新概念的**第一遍**：先自己读官方文档或手写最小例子，让 AI 讲会把「理解」替换成「听懂」。
- 调 bug 时还没读报错：先读，再问。
- 涉及安全的地方（鉴权、密钥、SQL 拼接）：必须自己写、自己审，AI 生成的鉴权代码是最容易埋漏洞的地方。

## 一句提醒

面试官不会问你「会不会用 AI 写代码」，会问「这段代码为什么这么设计」。**AI 能替你写，替不了你回答。**
