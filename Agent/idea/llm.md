# QKV
生成token时，模型会拿着当前token的Q(查询向量query)，去跟前面所有的token的key做匹配，找到匹配度最高的key，读取对应的value作为当前token
 - 第一步：计算点击词的概率
 - 第二部：softmax归一化成权重
 - 第三步：按权重加权求和

- 上下文越大，模型对每一条信息的“记忆力”就会越差 （上下文腐烂）


- KV Cache
已有 100 个 token，生成第 101 个 token：生成该位置的 Q，与前面 1‑100 的 K 做注意力点积，得到第 101 个 token，并算出该 token 对应的 K、V。

生成第 102 个 token 时，朴素实现会重新对 1‑101 所有 token 计算 K、V，1‑100 的 K/V 属于重复开销。
KV Cache 缓存已经计算完成的历史 K、V，推理时直接读取复用，只计算当前位置的 Q；每生成一个新 token，就把它的 K、V 追加到缓存中，大幅减少计算量。


# QKV

生成 token 时，模型会拿着当前位置的 Q（查询向量 query），去和所有可见位置的 K（键向量 key）做匹配。不是只挑匹配度最高的那个 key 读取对应的 value，而是每个位置都得到一个分数，softmax 归一化成权重后，把所有位置的 V（值向量 value）按权重加权求和，作为当前位置的输出。
- 第一步：计算 Q 与每个 K 的点积分数，除以 √d_k 做缩放，并用因果 mask 屏蔽未来位置，所以第 t 个位置只能看到 1..t（包含自己）
- 第二步：softmax 把分数归一化成权重，权重之和为 1
- 第三步：按权重把所有 V 加权求和
- 上下文越大，对每条信息的检索越不稳定：典型表现是中间的信息更容易被忽略，开头和结尾的信息更容易被用上，并不是每条信息都按固定比例衰减 （上下文腐烂）
- KV Cache
已有 100 个 token（prompt 阶段所有 token 的 K/V 已并行算好并缓存），生成第 101 个 token：用第 100 个位置的 Q，与缓存里 1..100 的 K 做注意力计算，采样得到 token101；此时 token101 的 K、V 还没算，要到下一步才算并追加进缓存。
生成第 102 个 token 时，把 token101 输入模型，算出这一位置的 Q、K、V；Q 与 1..101 的 K（1..100 从缓存读取，K101 本步新算）做注意力得到 token102，然后把 K101、V101 追加进缓存。朴素实现每一步都会重算 1..t 全部 token 的 K、V，其中 1..100 属于重复开销。
KV Cache 缓存已经计算完成的历史 K、V，推理时直接读取复用；当前位置只新算 Q、K、V（不是只算 Q）：Q 用来查询，K/V 追加进缓存。这样省掉历史 K/V 的重复计算，但新 token 仍要和 1..t 的所有 K 做点积，注意力本身还是随上下文变长而变慢，缓存也会占用随层数、头数、长度增长的显存。
